# Gatehouse service SMS — release notes for the operator

## Scope and existing production paths

The implementation is based on main at 9bd6f874823fe3f1f81e07a40313aae0b64eccf9. The earlier mobile and payment audit is a separate change set. This branch includes its private HTML entry point and token stripping so that landing on an SMS link does not load marketing scripts. Retain these changes when merging both branches.

| Production operation | Source used for the integration |
|---|---|
| Submit a request, store phone | Quote.tsx → send-contact-email.ts → gh_visits. The existing client_contact event in gh_events holds the phone. Only a new insert carrying the current explicit consent enrolls a customer. A phone correction invalidates the number. |
| Save a card | create-checkout-session.ts, card-status.ts, stripe-webhook.ts. Saving a card never generates a booking confirmation or payment receipt SMS. |
| Confirm a date, accept an alternative | booking-action.ts and visit.ts write visit_confirmed. This event schedules confirmation or rescheduling and the reminders. Repeat writes for the same agreement are ignored. |
| Assign or cancel | booking-action.ts and visit.ts update the visit. A cleaner must have opted in through their own protected portal for the active roster phone. |
| Publish the photos | cleaner.ts or booking-action.ts publishes a report. A draft or a submission without a tracked report email does not trigger a payment request. |
| Issue and re-clean | report.ts, booking-action.ts and the inbound reply flow update issue_open, issue_ever, report_status or the re-clean assignment. A returned report or scheduled re-clean asks the responsible contractor to act. |
| Successful payment | The payment obligation handler, verified Stripe webhook and reconciliation worker persist paid status, paid time and PaymentIntent. Starting a payment cannot enqueue a receipt. |
| Existing timers and email | auto-charge.ts and Resend retain their original responsibilities. SMS status never authorizes a charge, restarts the report clock or marks an email delivered. |

On November 23, the schema visualizer for the accessible Supabase project gatehouse-test showed gh_visits, gh_photos, gh_events, gh_cleaners, gh_visit_access and gh_webhook_events. We verified the visit columns for successful payment, waived charges, re-cleans, tracked report mail, issues and cleaner-link expiry. We did not apply the migration there or verify which Vercel environments use this project.

The migration subscribes to real transactional row and journal changes. The phone, role, source, disclosure version and time are recorded in gh_sms_consents. The template never includes an address, entry instructions, photos or a permanent owner/cleaner key. Client links resolve into the existing booking portal. Cleaner links expire in 24 hours or at the underlying assignment expiry, whichever comes first. Opening an old link also checks the current recipient, assignment, token generation and opt-out. Existing portal session rules apply after a successful exchange.

## Sender choice

1. Quo Hosted SMS. Twilio provides a number-specific eligibility check. Existing messaging with another provider can preclude hosting. We have no positive eligibility result for this number and no agreement from Quo allowing split routing. Keep the existing route intact.
2. Separate verified Twilio toll-free sender for service SMS and the existing Quo voice number. This is the configuration the code supports. Use one dedicated Messaging Service with exactly one verified US toll-free sender. Twilio documents a sole-proprietor exception to its US business-registration-number rule. Approval for this owner's business and residence has not been established.
3. A full port would transfer the number to the new provider. Quo supports port-outs and the number must remain active during a port. A port and migration of voice routing are separate owner decisions.

Sources: [Twilio hosted number eligibility](https://www.twilio.com/docs/phone-numbers/hosted-numbers/hosted-numbers-api/eligibility-resource), [Hosted Numbers FAQ](https://www.twilio.com/docs/phone-numbers/hosted-numbers), [Quo porting](https://www.quo.com/porting), [Twilio toll-free verification](https://www.twilio.com/docs/messaging/compliance/toll-free/console-onboarding), [registration numbers and sole proprietors](https://help.twilio.com/articles/38266268244507), [Twilio opt-out behavior by sender type](https://help.twilio.com/articles/360034798533-Getting-Started-with-Advanced-Opt-Out-for-Messaging-Services), [webhook signature validation](https://www.twilio.com/docs/usage/security).

Before spending money, the account holder can ask Twilio Support: “I operate Gatehouse Home Cleaning in Georgia as a sole proprietor without an EIN and manage it from Belarus. Can my account qualify for US toll-free verification for transactional SMS to US customers and contractors? Which business address, identity and operating-location evidence do you accept for my circumstances?” Supply accurate details using Twilio's own verification form. The US address alone does not establish eligibility. Do not attach identity documents to the repository.

## Deploy and exercise the pilot

1. Apply schema migrations in order to an isolated preview database. Execute supabase/tests/transactional-sms.sql there. Production must receive 20261123_transactional_sms.sql before the new opt-in form goes live. There is no backfill of customer or contractor consent.
2. Use a stable HTTPS preview origin, a separate test database and an eligible test sender. Set server-only TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_MESSAGING_SERVICE_SID, TWILIO_SMS_NUMBER (E.164), SMS_PUBLIC_ORIGIN (no trailing slash), SMS_LINK_SECRET (random server secret) and SMS_CRON_SECRET. Reuse the project's existing Supabase and portal-link credentials. Never expose these values in VITE_ variables, logs, PRs or chat. Enable the optional consent controls with VITE_SERVICE_SMS_ENABLED=true at build time only after applying the database migration. Leave SMS_MODE unset for disabled sending. SMS_MODE=pilot permits delivery only to SMS_PILOT_PHONE. SMS_MODE=live suppresses visits marked is_test.
3. Configure the inbound Messaging Service webhook to POST to /api/visit?sms=1 on the exact public origin. Forward all inbound fields. The worker supplies its per-message status callback. Twilio signs the exact externally configured URL and form. Avoid redirects. The same existing Vercel function handles the protected worker GET, link exchange and webhook POST. No new publicly deployed function is required.
4. In preview manually call the worker on that preview with its bearer credential. For production put SMS_CRON_SECRET in the production Supabase Vault under gatehouse_sms_worker and run supabase/operations/enable-production-sms-dispatch.sql as the database administrator. Its fixed destination is the production Gatehouse domain. Newly queued events wake the worker after commit via pg_net. A named pg_cron job checks once per minute for due jobs and retries. Run this activation only after the verified sender and pilot configuration are ready. Monitor net._http_response and cron.job_run_details during the pilot.
5. In an authorized pilot, use only the owner's verified US phone, an isolated visit and test payment data. Confirm consent off/on, assignment and fresh links, cancellation, report and payment gates. Observe the Message SID and final delivery callback. From the handset reply STOP, try a subsequent service event, then START and HELP. For US toll-free, carrier filtering and responses can occur outside Twilio. Check the actual phone, Twilio logs and local suppression state. If the carrier withholds START or STOP, do not manually clear a suppression or authorize commercial rollout on the strength of a trial console message.
6. Set live mode only after account and sender approval, a successful actual pilot, and owner approval for paid usage. Quo is outside this deployment. Stop sending by removing SMS_MODE or disabling the scheduler. Email, booking and payment flows continue to use their existing handlers.

## Delivery and troubleshooting

- The database rechecks a job on claim and after Twilio Lookup verifies the country as US. In-flight provider requests cannot be recalled. Unknown provider acceptance, including timeouts and 5xx, goes to reconciliation. Never blindly replay it. Look up the recorded SID or compare the recipient and submission time in Twilio's private console. HTTP 429 and safe pre-submission failures use bounded backoff. Callback retries, status reordering and a callback arriving before the send response are handled.
- Due times use Atlanta local windows and the report publication time. Use an explicit arrival window such as “8–10 AM” or morning/midday/afternoon for 24-hour reminders. Arbitrary free text with no identifiable start time cannot schedule an exact reminder. Late visit reminders expire after one hour, and the 20-hour reminder expires at 24 hours. Pending notifications can expire during outages.
- Review gh_sms_jobs by state, delivery, error_code and attempted_at. Jobs and their attempt history expire 30 days after the delivery window. Positive consent evidence and opt-out records are retained separately. Signed URLs, message bodies, credentials and photos are not recorded in gh_sms_history. Restrict provider log access and configure provider retention for the business.
- Production Supabase state, credentials, Vercel routing, carrier delivery and phone behavior need separate live verification. Automated tests use synthetic recipients and simulated Twilio network responses.
